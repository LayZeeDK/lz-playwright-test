## 1. Prior art for mutating JSX or React component code

Headline: no mutation testing tool, plugin, fork or paper found mutates JSX markup (text, attributes, elements). Every JavaScript mutation tool opened, StrykerJS included, deliberately skips strings inside a `JSXAttribute`, and that rule has spread unchanged from a 2018 StrykerJS issue into four tools released in 2026. The one upstream request for JSX text mutation (StrykerJS #4375) is open, stale-labelled, and was declined by a maintainer in 2023. The operator ideas in the design have therefore no implemented precedent at the JSX level; their nearest relatives are the live-DOM operators already covered in `playwright-mutation-operators.md` section 1.

### 1.1 StrykerJS: the upstream record

Read with `gh issue view <n> --comments` and in the local clone `D:/projects/github/stryker-mutator/stryker-js` at tag `v10.1.1`.

- **#4375 "Possibility to mutate string nodes in JSX/TSX"** (limonte, 2023-07-20, open, labelled Feature request and stale; stale-marked 2025-01-31 and 2026-06-28) [checked: https://github.com/stryker-mutator/stryker-js/issues/4375]. Asks that `<p>This is a basic component</p>` be mutated, because Jest and Stryker both report 100% while the test only checks `getByText('Hello there')`. JimLynchCodes (2023-08-03) proposed four JSX mutators, "delete each element", "delete attribute of each element", "replace attribute value of each element with different value", "change inner html of each element", and noted they apply "to mutation testing of any markup language (like Angular or regular html files)". odinvanderlinden (contributor, 2023-09-01): "Currently we support mutating Javascript statements inside JSX. For now we don't have plans to implement mutating HTML elements inside JSX in the near future as this is Stryker for Javascript and not Stryker for HTML. Though in the future we would like to add the possibility for StrykerJS users to create their own mutators just like in Stryker.NET." After limonte pointed out that JSX compiles to `React.createElement('p', { children: '...' })`, the reply was: "If we are going to mutate strings inside babel we are basically testing if babel works correctly" and "the strings we write inside these HTML like JSX elements are constants because they can't change". kcmr (2025-02-18) supported the request: it would stop tests "relying solely on the existence of DOM nodes queried by attributes (e.g., `data-testid`)". No maintainer reply since 2023. The reproduction repo `limonte/stryker-sandbox` is gone (`gh api repos/limonte/stryker-sandbox` returns 404) [checked]. What this means for the design [inferred]: the upstream objection is one of scope ("JavaScript, not HTML"), not of mechanism; the proposed operator list is a subset of the design's (element removal, attribute removal, attribute value change, text change), and the design's Angular-template ambition matches the "any markup language" remark.
- **#701 "TS StringLiteralMutator should not mutate JSX attribute's strings"** (simondel, 2018-04-16, closed 2018-04-20) [checked: https://github.com/stryker-mutator/stryker-js/issues/701]. The origin of the exclusion the design works around. Example given: `<Record class="row" />` produced `<Record class="" />`. simondel: "if we had come across this feature/bug during the development of the TypeScript mutator, we would probably have decided not to mutate the JSX elements like we do now"; the fix copied "the same check on JsxAttributes that is used in the stryker-javascript-mutator". The check survives in the instrumenter: `git log --all -S JSXAttribute -- packages` lists `4d15e0290 feat(Mutator): Add StringLiteral mutator (#690)` through `cb3bd8fe2 v10.0.0`, and at `v10.1.1` `git grep -i jsx -- packages/instrumenter/src` finds exactly three lines: the skip in `mutators/string-literal-mutator.ts:38`, the `.jsx` case in `parsers/create-parser.ts:58`, and the `jsx` Babel plugin in `parsers/js-parser.ts:24` [checked]. No mutator visits a JSX node.
- **#4141 "More control over context where mutations should apply"** (2023-04-27, closed stale) [checked: https://github.com/stryker-mutator/stryker-js/issues/4141]. A React and TypeScript proof of concept found "styling relevant JSX attributes will be mutated" and that disable comments "are not working at JSX"; the team's fallback was to stop mutating `*.{jsx,tsx}`. nicojs pointed to `// Stryker disable` docs and to #3229, which shipped as Ignore plugins in StrykerJS 7.3 (2023-10) [checked: https://github.com/stryker-mutator/stryker-js/issues/3229]. So the one JSX-specific complaint that reached the maintainers was about too many JSX mutants, and the answer was a plugin kind that can only remove mutants. The comment failure matches the directive finding in the design ("JSX comment directives are ignored for every mutator").
- **#525 "Add React support"** (2017-12 to 2018-05) [checked: https://github.com/stryker-mutator/stryker-js/issues/525]: a tracking issue (Babel transpiler, "Don't crash when users try to mutate JSX #545", Webpack, test on React projects), closed when users reported working setups. No operator discussion. **#2568** and **PR #2577** (2020-10) [checked: list output; PR title "Add missing case for .jsx files in parser"] restored `.jsx` parsing after the 4.0 rewrite. `docs/guides/react.md` at `v10.1.1` is configuration only and says nothing about what JSX gets mutated [checked]. The Stryker blog (46 posts listed from `stryker-mutator/stryker-mutator.github.io/blog`) has no React or JSX post [checked: file list only].
- PR search `gh pr list --search JSX` over the whole history returns only dependency bumps besides #2577 [checked].

Outside JavaScript, the same family draws the same line: Stryker.NET's tracker has Blazor and Razor issues only about compiling against the Razor source generator (#1486 "Support for blazor", closed; #3605, #3813), none about mutating Razor markup [checked: issue titles from `gh issue list --search razor|blazor`; bodies not opened].

Pointer outside the JSX question: `mizchi/mutator`'s `--runner playwright` (README section "Playwright (experimental)") compiles mutants into the Vite-served modules once, adds an init script to each test's browser context that activates the mutant and, in the dry run, records reached mutants, keeps the record across same-origin navigations through `sessionStorage`, reads every page and frame when the test ends, and runs each mutant as one `playwright test` process with one worker, `--retries=0` and `--max-failures=1`; a mutant run on its fixture app takes "about 1–2 s" and starting Playwright "costs about 0.6 s per run" [checked: README lines 336-367]. That is the same shape as this repository's runner and `prior-art-mutation-e2e.md` section 6 items 1 to 3, built independently two weeks before this research. It does not change the JSX design.

## 3. What this changes for the operator design and the synthetic cases [inferred]

For the operator design:

1. **No precedent to align names or semantics with.** No tool mutates JSX markup, so the StrykerJS-style names in the design stay the only naming source; the four operators proposed in #4375 (delete element, delete attribute, replace attribute value, change inner html) map onto `ElementRole`/`ConditionalElement`, `LabelAttribute`/`UrlAttribute`/`HiddenAttribute`, `StateAttribute`, and `TextLiteral`, which is a reason to cite #4375 in the upstream PR and in the README as the user demand.
2. **Expect the "JavaScript, not HTML" objection upstream.** The 2023 refusal was about scope, not mechanism, and the same maintainer wanted user-defined mutators "like in Stryker.NET". The upstream path in the design (neutral placer fixes first, operators off by default behind `includedMutations`) answers that objection directly; the PR text should say the operators ship disabled.
3. **The `JSXAttribute` string exclusion is an ecosystem convention, not a StrykerJS quirk.** Five independent 2026 tools copied it. The design's choice to mutate attribute values by meaning (label, URL, disabled, hidden, state) instead of as strings is what distinguishes it from the mutant #701 removed (`class="row"` to `class=""`), and the README should say so: `className`, `style`, `data-testid` and `key` are never mutated.
4. **Ignore plugins are the upstream answer to JSX noise.** #4141 led to #3229 and Ignore plugins; the design already uses the `Ignore` kind for fail-loud. A user-facing `Ignore` example that drops UI mutants in a folder may be worth one paragraph of docs, nothing more.
5. **mootant's template support shows the reachable next step.** It mutates Svelte and Vue template expressions, not static markup, with HTML-comment directives. The design's "later: Angular templates" item has that precedent for expressions and still none for static attributes and text.
6. **FragGen's visible/invisible split and MaewU's results back the existing skips** (non-letter text, `data-testid`, `className`), nothing new to add.

For the synthetic cases:

7. **Copy shapes, do not vendor repos.** All eight apps fail the 1.63 rule as declared or are multi-browser or need a backend. The fixture set should be a handful of TSX files modelled on TodoMVC TypeScript-React (non-inline handlers, `htmlFor` + `placeholder`, `{clearButton}` child), epic-stack (`aria-label` on `<Link>`, `sr-only` text as the only accessible name, `<Link to="edit">` + `toHaveURL`) and octochangelog (icon link with `aria-label` + `href`, a ternary with `toBeVisible` and `toBeHidden`).
8. **Add three known-survivor cases**, each from a real app: `htmlFor` emptied while a placeholder still names the control (epic-stack search bar); `htmlFor` emptied on a label that wraps its input (Next-js-Boilerplate); `ConditionalElement` forced true where the test already runs the true branch (epic-stack `canDelete`, Next-js-Boilerplate error message). The verification plan's must-not-generate rows do not cover these; they belong in a "generated but expected to survive" list so a surviving mutant there is not read as a bug.
9. **One absence assertion per conditional fixture.** Only octochangelog's `compare.spec.ts` asserts `toBeHidden()`; every other suite only asserts presence, which is why forced-render mutants survive. The fixture tests should pair each `ConditionalElement` case with a `toHaveCount(0)` or `toBeHidden()` test so the operator's kill path is exercised at least once.
10. **`StateAttribute` needs a hand-written fixture.** In ariakit the ARIA state is set inside the library and in the other apps it is absent; no real-app shape was found where the example JSX writes `aria-expanded`, so the fixture must supply one (a disclosure button with `aria-expanded={open}`), and the test must use `getByRole(..., { expanded })` or `toHaveAttribute`.
11. **Locator-style control.** Keep conduit-ui's CSS-locator pattern as one negative fixture (`locator('a:has-text(...)')`, `textarea[placeholder=...]`) to show which operators a non-role suite still kills (`UrlAttribute` through `href` selectors, `LabelAttribute` through placeholder selectors) and which it misses (`ElementRole`, `StateAttribute`).
