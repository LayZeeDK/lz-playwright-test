### 1.1 Operator catalogues

**Mutandis** (Mirshokraie, Mesbah, Pattabiraman, ICST 2013) [checked by worker: ICST'13 PDF via Wayback, Tables III-V; repo `saltlab/mutandis` `JsCodeOperators.java`, `DomJsCodeLevelVisitor.java`]. Besides generic variable/branch/return operators and JS-specific ones (remove `var`, `this`, parseInt radix, `/g`; `setTimeout(f)` -> `setTimeout(f())`; `undefined` -> `null`), Table V has DOM/jQuery/XHR operators: swap `insertBefore`/`replaceChild` arguments; change the id or tag in `getElementById`/`getElementsByTagName`; change the attribute name in `set/get/removeAttribute`; swap `innerHTML` and `innerText`; swap `#`/`.` in jQuery selectors; change the class/property name in `addClass`/`removeClass`/`attr`/`prop`/`css`; change XHR method, URL, async flag, and the compared `readyState`/`status`. These target imperative DOM code, which modern React/Angular apps rarely write; the transferable ideas are attribute-name and class-name changes and request method/URL changes. [inferred]

**webMuJava** (Praphamontripong and Offutt; final set in Praphamontripong's 2017 GMU dissertation, Table 4.1) [checked by worker: dissertation PDF https://digitalcollections.gmu.edu/record/77628/files/Praphamontripong_gmu_0883E_11475.pdf; 2010 paper via Wayback]. 15 operators: FOB (insert a dummy history entry so Back goes wrong), WLUR/WLUD (replace/delete an `<a href>` URL), WFUR (replace form `action`), WRUR (redirect URL), WCUR (JSP forward/include URL), WFTR (GET <-> POST), WPVD (drop an include parameter), WCTR (redirect <-> forward), WSCR (bean scope), WSIR (`getSession(true/false)`), WSAD (delete session attribute), WHID/WHIR (delete/replace hidden input), WOID (delete read-only input). Share of non-equivalent mutants left alive by conventional test sets from 12 testers: FOB 1.00, WPVD 0.88, WLUR 0.83, WLUD 0.81, WOID 0.78 ... WHID 0.25; WFUR, WHID, WLUD are redundant. Transferable to SPAs: link target, form action/method, hidden inputs, and history (Back) handling. [operators checked by worker; transfer inferred]

**MaewU** (Yandrapally and Mesbah, ICSME 2021) [checked by worker: https://yrahulkr.github.io/resources/papers/maewu.pdf, repo `yrahulkr/maewu`]. Mutates the live DOM during Selenium runs. 16 operators in 5 types: Attribute (AAM add, ADM delete, AMM modify: `id`, `class`, `href`, `src`, form `action`, input `type`), EventHandler (EHAM add, EHDM delete, EHMM modify), Tree (TIM insert, TDM delete, TMM move), Content (CIM insert, CDM delete, CMM modify), Style (SVM visibility, SCM colour, SPM position, SSM size). 300 mutants on six apps, 278 non-equivalent (93%), overall score of the existing suites 0.20. Per-operator score: AAM 0.00, ADM 0.20, AMM 0.42, EHAM 0.00, EHDM 0.00, EHMM 0.00, SCM 0.00, SPM 0.27, SSM 0.17, SVM 0.23, TDM 0.48, TIM 0.03, TMM 0.35, CDM 0.18, CIM 0.00, CMM 0.28 [checked by Claude: `maewu.txt:495-522`]. Event-handler mutants were never killed ("killing needs both performing the action and asserting its result"); tree deletion was easiest (locating the element is enough); colour mutants were mostly equivalent (child CSS overrides). [checked by worker]

**Ma11y** (Tafreshipour, Deshpande, Mehralian, Ahmed, Malek, ISSTA 2024) [checked by worker: abstract via an index; paper behind Cloudflare; operators read from the authors' repo https://github.com/mahantaf/web-a11y-tool-analyzer `src/mutant-generator/mutation-operators/F*.js`]. 25 live-DOM operators, each named after a WCAG failure technique, e.g. F2 `<h2>` -> styled `<p>`, F42 `<a href>` -> `<span onclick>`, F44 reversed `tabindex`, F54 `onclick` -> `onmousedown`, F55 `onfocus="this.blur()"`, F65 remove `alt`/`aria-label`/`title` from `<img>`, F68 remove `<label>` and `placeholder`, F77 duplicate `id`, F78 `outline:none`, F89 icon link loses its name, F91 `<th>` -> `<td>`, F96 `aria-label` differs from visible text. Its oracle is accessibility checkers (axe etc.), which "cannot identify nearly 50%" of injected bugs. Several map directly onto Playwright role/name queries (F2, F42, F65, F68, F89, F91, F96) and keyboard flows (F44, F54, F55). [operators checked by worker; acronym expansions and Playwright mapping inferred]

**Android and desktop GUI** [checked by worker]: MDroid+ (arXiv 1707.09038, Table 1) GUI-relevant operators: WrongStringResource, InvalidLabel, BuggyGUIListener (delete listener action), FindViewByIdReturnsNull, InvalidIDFindView, InvalidColor, InvalidViewFocus, ViewComponentNotVisible, LengthyGUICreation/Listener, LengthyBackEndService, NullBackEndServiceReturn, DifferentActivityIntentDefinition (navigation to the wrong screen), InvalidKeyIntentPutExtra (lost navigation parameters). Silva, Vergilio, Endo (JSERD 2022): six deletion operators negating WCAG criteria (MTS textSize, MIT inputType, MNFD nextFocusDown, MLF labelFor, MH hint, MIA importantForAccessibility); original suites killed 2 of 256 mutants, because the accessibility checker was the bottleneck. Oliveira, Alegroth, Gao, Memon (ICSTW 2015): 18 GUI operators in three classes, removing (REW remove widget, SWI set invisible, REL remove listener), adding (AIW/ASW identical/similar widget, which test locator uniqueness; ADW, AAL) and modifying (resize, move, overlap MLWO, MWA appearance, MWT widget type); 83.9% of GUI-operator mutants were GUI-visible versus 11.27% of muJava method-level mutants.

**JS event/Ajax** [checked by worker: repo `knishiura-lab/AjaxMutator` class names; meanings inferred]: AjaxMutator (Nishiura et al., SEKE 2013) mutates event attachment (EventTargetRA, EventTypeRA, EventCallbackRA), timers (TimerEventDurationRA), requests (RequestUrlRA, RequestMethodRA, success handler), DOM create/remove/clone to no-op, attribute name/value, and fakes a blank Ajax response body. Maezawa et al. ASE'14 add delay-based operators for async faults (two or three; the sources disagree).

### 1.2 Framework-specific work

- **Angular** (Augustin, Winkelmann, Kuchen, ENASE 2025, https://www.scitepress.org/Papers/2025/132039/132039.pdf) [checked by worker; full PDF]: 8 operators **implemented as StrykerJS extensions** on component/service TypeScript, not templates: `==`/`===` swaps, delete error handling (try/catch, `catchError`, subscribe error callback), reactive-form default values, delete form validators, rename a form-control name, delete `.subscribe(...)`, delete `unsubscribe()`/`take*`, swap an RxJS operator for an already-imported one. Evaluated with Jest unit tests (24 suites, 138 tests), not e2e [checked by Claude: `dl-papers/angular.txt:425-431`]. Results on one app: new operators 192 mutants, 19.79% killed; built-ins 1,114 mutants, 29.17% killed.
- **React**: a Sharif University thesis "Generating mutants for user interface testing in web based applications" reportedly proposes JSX operators (element -> Fragment, remove element, lifecycle/state/handler/ref operators) on 14 React programs; **not opened** (TLS/access errors), search snippets only.
- **Vue, JSX templates, CSS operator catalogues: not found** (queries in the part file). The only CSS mutation found is MaewU's runtime Style operators, Walsh/McMinn/Kapfhammer ASE'15 (responsive layout size rules; cited, not opened), and hand-made CSS mutants in Garousi et al. arXiv 2409.00411.

### 1.3 What the prior art implies for the operator design [inferred]

1. **Event-handler removal is the most valuable and the least killed operator class**: MaewU's EHDM scored 0.00, MDroid+ has BuggyGUIListener, Oliveira has REL (whose 13 mutants on the Calculator were all equivalent, 0% "good", per the worker's reading of Table V). It measures exactly what e2e suites skip: asserting the effect of an action.
2. **Link and navigation targets survive conventional suites** (webMuJava WLUR 0.83, WLUD 0.81, FOB 1.00 survival). `toHaveURL` after a click and Back-button tests kill them.
3. **Element deletion is easy to kill** (MaewU TDM 0.48 best), so it adds little signal for suites that locate the element at all; content changes need explicit text assertions (CMM 0.28, CIM 0.00).
4. **Style/colour mutants are mostly equivalent or visual-only** (SCM 0.00 with 7/22 equivalents), which supports leaving CSS for last.
5. **Accessibility operators are a new, Playwright-native niche**: Ma11y and Silva et al. used accessibility checkers as the oracle and found the oracle weak; Playwright's role/name locators are a stronger, test-integrated oracle for the same faults. No published work measures that.
6. **Source-level vs DOM-level**: MaewU and Ma11y mutate the live DOM (stack-agnostic, no build), whereas StrykerJS mutates source with schemata. Source-level operators can be reported against source lines and use per-test coverage; DOM-level ones cannot be tied to a source line, but need no instrumenter changes. Both can coexist (prior-art file idea 12).

### 2.2 The 17 mutators, read for UI effect

All mutators live in one hardcoded array, `allMutators` in `packages/instrumenter/src/mutators/mutate.ts:20-38` [checked]. Those with a UI-visible effect:

- **StringLiteral** (`string-literal-mutator.ts:8-51`) replaces a string with `""` (or `""` with `"Stryker was here!"`), and a template literal with an empty one. It **skips a string whose parent is a `JSXAttribute`** (line 38), so `aria-label="Close"`, `role="dialog"`, `href="/docs"`, `data-testid="close"`, `to="/help"` are never mutated; the same value written as `aria-label={'Close'}` is (the parent is then a `JSXExpressionContainer`). [checked; spike: `aria-label={'Search'}` and `href={'/docs'}` mutated, `aria-label="Close dialog"`, `data-testid="close"`, `to="/help"` not]
- **JSX text is never mutated.** `<h1>Edit items</h1>` is a `JSXText` node, which no mutator handles (`git grep -i -E 'await|jsx|attribute'` over `src/mutators` finds only line 38 above). [checked; spike: no mutant on any JSX text]
- **BooleanLiteral** (`boolean-literal-mutator.ts:9-24`) flips `true`/`false` and removes a prefix `!`. So `disabled={true}` and `useState(false)` are mutated; `disabled={busy}`, `aria-expanded={open}` and the bare `hidden` attribute are not. [checked; spike]
- **ConditionalExpression** (`conditional-expression-mutator.ts:23-93`) replaces an `if` test, a loop test, or a binary/logical boolean expression (`&&`, `||`, `===`, `<`, ...) with `true`/`false`; it does **not** touch a ternary's test (the `isConditionalExpression` branch is commented out at line 83), so `{busy ? <Spinner/> : <Idle/>}` and `{open ? 'block' : 'none'}` get no mutant when the test is an identifier. [checked; spike: L37 of `Dialog.tsx` got 0 mutants]
- **LogicalOperator** swaps `&&`/`||`/`??`. In JSX `{open && <p/>}` this yields `{open || <p/>}`. [checked]
- **Conditional rendering flips in JSX are partly covered, and one of them is misleading.** For `{open && <p role="status">Opened</p>}` the spike produced `true`, `false` and `open || <p/>`. React renders nothing for the booleans `true` and `false`, so the `true` mutant hides the element just like `false`; neither forces it to show. [checked: spike L36; React's boolean rendering rule is inferred from React semantics, not re-checked here]
- **ArrowFunction** (`arrow-function-mutator.ts:7-21`) turns an expression-bodied arrow into `() => undefined`. That empties an inline handler `onClick={() => setOpen(true)}` and a list render `items.map((i) => <li/>)`. A handler passed by reference (`onClick={close}`) gets no mutant at the attribute; only its body can be emptied by **BlockStatement** (`block-statement-mutator.ts:8-16`). [checked; spike L26, L38]
- **CallExpression** (`empty-expression-mutator.ts:14-49`, named `CallExpression` on line 15) removes a call statement (`e.preventDefault();` -> `;`) or a `throw new X()`, **but only when it is the only mutant in that statement's subtree** (`filter: mutantsInScope.length === 1`, lines 46-48; applied in `babel-transformer.ts:122-153`). So `el.focus();` survives as a statement when the call has a string argument (`getElementById('trigger')!.focus()` got only a StringLiteral mutant), `setOpen(false);` gets only the BooleanLiteral, and `router.navigate(['/done'])` gets only ArrayDeclaration and StringLiteral. [checked; spike L9, L15-16, L22 of `dialog.component.ts`]
- **No mutator removes `await`** (no mutator matches `AwaitExpression`), and `await save();` / `await navigate('/done');` are not call statements, so they are never removed. [checked; spike L10-11]
- **ObjectLiteral** empties `{ method: 'POST', body }` in `fetch` options and `style={{ display: ... }}`; **MethodExpression**, **ArrayDeclaration**, **EqualityOperator**, **ArithmeticOperator**, **UpdateOperator**, **AssignmentOperator**, **UnaryOperator**, **Regex**, **OptionalChaining** work on JS semantics only. [checked]

## 3. Extension points and integration routes

### 3.1 No mutator plugin kind

- `PluginKind` has exactly `Checker`, `TestRunner`, `Reporter`, `Ignore` [checked: `packages/api/src/plugin/plugin-kind.ts:4-9`]. An `Ignore` plugin can only suppress mutants (the built-in `angular` ignorer is one: `packages/instrumenter/src/frameworks/angular-ignorer.ts:19-30`, registered in `frameworks/index.ts:5-7`).
- The custom-mutator requests were all closed stale: #444 "Custom mutators as plugins" (2017; nicojs then: custom mutators "high on the priority list" once there is one AST), #2794 "Plugin API to custom mutators" (2021; nicojs: "I might like a custom mutator API in the future, but I'm hesitant to also open-up our parser and mutant-placer APIs here"), #169 (2016). [checked: `gh issue view 444|2794 --comments`]
- #5156 "Support mutating angular HTML templates?" is **open** (2025-01-31). nicojs: mutant schemata cannot "conditionally change the HTML" because Angular has its own compiler; mutating expressions inside the template would be possible via `angular-html-parser`, but "there is no way to access the `globalThis` object" from a template, "so we would need to somehow publish the active mutation on each component". A commenter proposed an `[stryker-mutant-switch]` directive with `*strykerBaseline` / `*strykerMutation="1"` containers backed by a service. A 2026 comment by lo1tuma points to #2269 (old mutator API removed in the mutation-switching rewrite) and to `@hughescr/stryker-llm-mutator`, which "works around the missing API by monkeypatching `@stryker-mutator/instrumenter` internals". [checked: `gh issue view 5156 --comments`]

### 3.2 What core accepts

- Core instruments in-process: `injector.injectFunction(createInstrumenter)`, then `instrumenter.instrument(files, { ignorers, ...options.mutator })`, writes `instrumentResult.files` into the sandbox, and provides `instrumentResult.mutants` as `coreTokens.mutants`. No later step adds mutants. [checked: `packages/core/src/process/2-mutant-instrumenter-executor.ts:64-73, 103, 117-121`]
- So **core runs exactly the mutants returned by `Instrumenter.instrument()`**, whoever generated them. A switch injected into the code that is not in that list is never activated or reported. Conversely, anything that changes the returned list (and the matching file content) is planned, run and reported like a built-in mutant. [inferred from the checked lines]
- `createInstrumenter` hard-wires `createParser`, `transform` and `print` (`packages/instrumenter/src/create-instrumenter.ts:21-30`) and the package `exports` map exposes only `.` and `./package.json` (`packages/instrumenter/package.json:11-14`). [checked]
- Plugins are imported in the main process before instrumentation (`1-prepare-executor.ts:70-78` loads `options.plugins` + the framework and reporter plugin files; instrumentation happens in the next executor). [checked]
- The report needs the file in `project.files` and derives `language` from the extension: `.ts/.tsx` -> typescript, `.html/.vue` -> html, everything else javascript (`packages/core/src/reporters/mutation-test-report-helper.ts:323-331, 366-378`). [checked]

## 4. Which Playwright locators and assertions observe which change

Source: `D:/projects/github/microsoft/playwright` at `v1.64.1`.

### 4.1 Matching rules that decide whether a mutant can be seen

- **`getByRole`** matches role (explicit or implicit) plus optional accessible `name`/`description` and ARIA states (`checked`, `disabled`, `expanded`, `level`, `pressed`, `selected`); name matching is "case-insensitive and searches for a substring" unless `exact`; by default "only non-hidden elements, as defined by ARIA, are matched" (`includeHidden: false`). [checked: `docs/src/api/params.md:1481-1560`; `docs/src/locators.md:192, 263`] Consequences [inferred]: emptying a name (`""`) is killed; changing case or appending text is not; hiding an element from the accessibility tree (`aria-hidden`, `display:none`, `hidden`) is killed by any `getByRole` that targets it, even with no visibility assertion; changing `role` is killed; flipping `aria-expanded`/`aria-pressed`/`aria-checked`/`aria-selected` is killed only if the test passes that option or uses `toMatchAriaSnapshot`.
- **`getByText`** normalises whitespace always, matches substring case-insensitively by default, matches `<input type=button|submit>` by `value` [checked: `params.md:1470-1474, 1739-1741`], and **does not skip hidden elements**: text matching skips only `SCRIPT`, `NOSCRIPT`, `STYLE` and `<head>` content [checked: `packages/injected/src/selectorUtils.ts:59-62`]. So a hide mutant survives `expect(getByText(...)).toHaveText(...)`; it is killed by an action (visibility check) or `toBeVisible`. [inferred]
- **`getByLabel`** uses `<label>`, `aria-labelledby` or `aria-label` [checked: `params.md:1777`]. **`getByTestId`** uses `data-testid` (configurable `testIdAttribute`) [checked: `params.md:1621-1631`]. Test ids are deliberately stable, so mutating them measures nothing about behaviour; they are only good as locator anchors. [inferred]
- **Actions** auto-wait: `click`/`check`/`tap` require exactly one element, Visible, Stable, Receives Events (hit-target check) and Enabled; `fill` requires Visible, Enabled, Editable; `focus`, `press`, `dispatchEvent` have no checks [checked: `docs/src/actionability.md:11-41`]. Visible = non-empty bounding box and not `visibility:hidden`; `display:none` and zero size are not visible; `opacity:0` **is** visible [checked: `actionability.md:81-88`]. Disabled = `[disabled]` on form controls, inside a disabled `<fieldset>`, or descendant of `[aria-disabled=true]` [checked: `actionability.md:94-101`]. Consequence [inferred]: mutants that hide, disable, zero-size or overlay an element the test clicks are killed by the click itself (as a timeout, not an assertion failure); `opacity:0` and `pointer-events` changes on non-clicked elements need `toHaveCSS` or screenshots.
- **Web-first assertions** retry until the expect timeout, 5 s by default [checked: `docs/src/test-assertions-js.md:23`]. Consequence [inferred]: delay mutants shorter than the timeout are equivalent for these tests; removing a loading state or an `await` is killed only if the test asserts the intermediate state or the ordering.
- **`toMatchAriaSnapshot`** records role, accessible name, ARIA attributes (`checked`, `disabled`, `expanded`, `invalid`, `level`, `pressed`, `selected`), text, and link `/url`; comparison is case-sensitive with whitespace normalised; partial templates may omit names and attributes [checked: `docs/src/aria-snapshots.md:146-160, 214-245`]. It is the one non-visual assertion that kills `href` changes and ARIA state flips without the test naming them.
- Full assertion list (locator: `toBeAttached`, `toBeChecked`, `toBeDisabled`, `toBeEditable`, `toBeEmpty`, `toBeEnabled`, `toBeFocused`, `toBeHidden`, `toBeInViewport`, `toBeVisible`, `toContainClass`, `toContainText`, `toHaveAccessibleDescription`, `toHaveAccessibleErrorMessage`, `toHaveAccessibleName`, `toHaveAttribute`, `toHaveClass`, `toHaveCount`, `toHaveCSS`, `toHaveId`, `toHaveJSProperty`, `toHaveRole`, `toHaveScreenshot`, `toHaveText`, `toHaveValue`, `toHaveValues`, `toMatchAriaSnapshot`; page: `toHaveTitle`, `toHaveURL`, `toHaveScreenshot`, `toMatchAriaSnapshot`). [checked: `docs/src/api/class-locatorassertions.md`, `class-pageassertions.md` method headings]

## 5. Mutating the Playwright tests themselves

### 5.1 Prior art

- **Extreme mutation / pseudo-tested methods** [checked by worker]: Niedermayr, Juergens, Wagner, CSED'16 (https://arxiv.org/pdf/1611.07163) delete a method's whole body (void) or return fixed values (`false`/`true`, `0`/`1`, `""`/`"A"`); a method none of whose mutants is killed is "pseudo-tested". Vera-Perez et al., EMSE 2018 (https://arxiv.org/pdf/1807.05030) and PIT's Descartes engine (https://github.com/STAMP-project/pitest-descartes, `mutation-operators.md`): operators `void`, `null`, `empty` (array), configured constants, `new`, `optional`, `argument` (return first parameter), `this`. These mutate the **application**, not the test, but answer the question test mutation asks ("does any test observe this code?") at much lower mutant counts. JS analogue for e2e [inferred]: empty a function body, return `undefined`/`null`/`''`/`0`/`false`/`[]`/`{}`/a resolved Promise; StrykerJS already has BlockStatement (empty body) and ArrowFunction (`() => undefined`), which are the `void` operator.
- **Oracle weakening** [checked by worker through the survey Hossain and Dwyer, arXiv 2212.06118; original not opened]: Schuler and Zeller, ICST'11 removed 0/25/50/75/100% of assertions and showed checked coverage dropped most sensitively. Jahangirova et al. ISSTA'16 (oracle assessment with mutants) and Fraser and Zeller's muTEST: search summaries only.
- **Locator mutation**: no paper defines operators that loosen or alter locators in Selenium/Playwright specs [checked by worker: queries in the part file]. Closest: Oliveira's AIW/ASW (add identical/similar widget, testing locator uniqueness), MaewU's discussion proposing its operators to expose fragile locators and weak oracles (future work), and hand-made "CSS-locator change" mutants in Garousi et al. arXiv 2409.00411.
- **Test-side tools for Playwright** [checked: READMEs from `registry.npmjs.org/apophasis` (1.0.5) and `registry.npmjs.org/playwright-mutation-gate` (0.3.3)]:
  - `apophasis` intercepts the module loader, patches `expect` in memory and **inverts every assertion** (`expect()` <-> `expect().not`), runs once with `APOPHASIS_MUTATE=true` and once without; a passing inverted run means the assertion is "weak or non-binding". It recommends lowering `expect.timeout` under mutation (inverted web-first assertions wait the full timeout before failing) and warns that short timeouts can let mutants survive.
  - `playwright-mutation-gate` inverts only the assertion marked `// @primary-assert` in a temporary copy of the spec and re-runs that test; reports killed / survived / cannot-mutate; fails CI on unmarked tests by default; cost is one `playwright test` run per marked assertion.

### 5.2 Test-side operators for Playwright specs [inferred unless marked]

| Operator | Before -> after | What a survivor means |
|---|---|---|
| `AssertionNegation` (as apophasis/mutation-gate) | `await expect(loc).toBeVisible()` -> `.not.toBeVisible()` | The assertion passes either way: it runs before the state changes, or the locator matches something that is both/neither |
| `AssertionRemoval` | delete an `expect(...)` statement | No other step depends on that assertion; the test still passes when it checks nothing (pair with an app mutant to learn whether the assertion was the only killer) |
| `AssertionWeakening` | `toHaveText('Saved')` -> `toBeVisible()`; `toHaveCount(3)` -> `toBeVisible()`; `toHaveURL('/done')` -> removed | The precise value is not needed by any app mutant kill: only measurable together with app mutants |
| `LocatorNameDrop` | `getByRole('button', { name: 'Save' })` -> `getByRole('button')` | Survives when only one button exists (fine); fails with a strict-mode violation otherwise (Playwright requires one match for actions, [checked: `actionability.md:12`]) |
| `ExactLoosen` | `{ exact: true }` -> removed; regex anchors removed | The exactness was not needed |
| `WaitRemoval` | delete `await page.waitForResponse(...)` / `waitForURL` | Web-first assertions already wait; mostly equivalent; a failure exposes an ordering dependency |
| `TimeoutShrink` | `expect.timeout` 5000 -> 500 | Not a strength measure; flags tests that depend on slow UI (apophasis notes the trade-off) |

How it fits the runner [inferred]:

1. Test mutation needs no instrumenter or activation channel: patch `expect` in the worker (apophasis's loader hook) or rewrite the spec file. It is orthogonal to the Stryker runner and can live in a separate command.
2. Its unique value over app mutation is cheap localisation: a survived `AssertionNegation` points at one line in one spec. App mutants say "nothing caught this change" without saying which assertion should have.
3. The combination worth building later is the **assertion-attribution** view: for each killed app mutant, record which `expect` failed (Playwright's JSON reporter has the error location per test). Assertions that never kill any app mutant are the hollow ones, which is a stronger signal than negation because it uses real faults. This needs no test mutation at all, only result bookkeeping in the runner.
4. Equivalent-mutant risk for negation is low for presence assertions and high for timing (`not.toBeVisible()` on an element that appears later passes immediately), so negated assertions should run with the normal timeout or a reduced one, never zero, as apophasis warns.

## Feasibility in StrykerJS

### F.1 Spike results (route b-1, measured)

`inject-mutators.mjs` (scratchpad `spike/`) pushed five operators (`JsxAttributeRemoval`, `JsxAttributeString`, `JsxText`, `TernaryTest`, `AwaitRemoval`) into the live `allMutators` array of the installed `@stryker-mutator/instrumenter@10.1.1` and instrumented `samples/Dialog.tsx`. [checked: outputs `inject-output.txt`, `inject-output-fixed.txt`, `instrumented-Dialog.tsx.txt`, `instrumented-Dialog.fixed.tsx.txt`]

1. Injection works: 71 mutants, 44 from the custom operators; custom names appear as `mutatorName`. [checked]
2. **A mutator cannot target a JSX attribute's string value directly**: the built-in expression placer treats that `StringLiteral` as a placement site and puts a `ConditionalExpression` into `JSXAttribute.value`; Babel rejects it ("Property value of JSXAttribute expected node to be of a type [...] but instead got ConditionalExpression") and the instrumenter aborts the file. This is why the built-in StringLiteral mutator skips `JSXAttribute` parents. [checked]
3. Mutating at a non-expression node instead (`JSXAttribute`, `JSXOpeningElement`, `JSXText`) makes placement climb to the enclosing `JSXElement`, which duplicates the whole element per mutant (output grew from 1,468 to 10,535 characters). Worse, **for an element that is a JSX child the placer inserts a bare `ConditionalExpression` into `children`, and Babel prints it without braces**: the output re-parses, but `stryMutAct_9fa48("20") ? ...` becomes literal JSX text and every variant renders, so baseline tests would fail. [checked: `instrumented-Dialog.tsx.txt` lines 138-149]
4. Fix, also measured: wrap `allMutantPlacers`' `expressionMutantPlacer.place` (the array is frozen, the placer object is not) so that when the placement node's parent is a `JSXElement`, `JSXFragment` or `JSXAttribute`, it first replaces the node with a `JSXExpressionContainer` and places inside it. Then attribute values get attribute-level switches (`aria-label={stryMutAct_9fa48("31") ? "" : (stryCov_9fa48("31"), "Close dialog")}`), children get `{...}`, the file re-parses as TSX, and output dropped to 9,570 characters. [checked: `instrumented-Dialog.fixed.tsx.txt`; semantic correctness of the rendered output is inferred, not executed in React]
5. Remaining cost: element-level operators (attribute removal, text emptying, tag swap) still duplicate the element subtree per mutant. A dedicated placer that swaps only the attribute list or the text child would avoid it, but placers cannot be added without patching (frozen array). [inferred]

### F.3 The weapon-regex precedent (mutation logic in an external package)

Added at Lars's request ("Include D:\projects\github\stryker-mutator\weapon-regex in research about custom StrykerJS mutants/mutators"). Local clone `D:/projects/github/stryker-mutator/weapon-regex`, HEAD `268bcf6`, latest tag `v2.0.6` (2026-10-03); read only.

**How the instrumenter calls it** [checked: `packages/instrumenter/src/mutators/regex-mutator.ts` at v10.1.1]

- `import * as weaponRegex from 'weapon-regex'` (line 3); dependency `"weapon-regex": "~2.0.0"` in `packages/instrumenter/package.json:55`.
- The `Regex` `NodeMutator` (lines 33-55) owns all Babel work: it recognises a `RegExpLiteral`, or a string literal that is the first argument of `new RegExp(...)` (lines 15-22), reads flags (lines 24-29), and turns each returned pattern back into a Babel node (`types.regExpLiteral` / `types.stringLiteral`).
- `mutatePattern` (lines 57-70) calls `weaponRegex.mutate(pattern, flags, { mutationLevels: [1] })` and keeps only `mutant.pattern`. The library's per-mutant `name`, `description`, `location` and `replacement` are discarded: every regex mutant is reported as `Regex` with the whole new literal as replacement. Levels are hard-coded to `[1]`; users cannot choose them. A parse failure is caught, logged with a link to the weapon-regex issue tracker, and yields no mutants.

**How weapon-regex structures mutators** [checked]

- `trait TokenMutator { name; levels: NonEmptySet[Int]; description(original, mutated, location); mutate(token: RegexTree): Seq[Mutant] }` (`core/src/main/scala/weaponregex/model/mutation/TokenMutator.scala:7-36`).
- `case class Mutant(pattern, name, location, levels, description, replacement)` (`Mutant.scala:56-63`): the full mutated pattern, a human name, a `mutationtesting.Location` inside the pattern, the levels, a description, and the changed fragment.
- 22 built-ins in `BuiltinMutators.all` (`core/src/main/scala/weaponregex/mutator/BuiltinMutators.scala:14-37`), indexed `byName` (class name) and `byLevel`; example `BOLRemoval`, levels 1, 2, 3, `^a` -> `a` (`internal/mutator/boundaryMutator.scala`).
- Pipeline: parse to a `RegexTree` (two flavours, JS and JVM), then apply the selected token mutators filtered by level (`WeaponRegeX.scala:25-30`, `scalajs/weaponregex/WeaponRegeXJS.scala:37-46`, which throws on a parse error).
- The JS API (`index.d.ts:27-120`) exposes `mutate(pattern, flags?, options?)`, `MutationOptions { mutators?, mutationLevels?, flavor? }`, `BuiltinMutators.all/byName/byLevel/atLevel(s)`. A JS caller can only select built-in mutators: `MutationOptionsExtension.scala:21-24` unwraps `TokenMutatorJS.tokenMutator`, a private Scala field (`TokenMutatorJS.scala:12`); there is no way to pass a JS-defined mutator.

**What the pattern implies for a Playwright/UI mutator library** [inferred from the checked facts above]

- The split is clean and reusable: the external library is a pure function from a **string in a sub-language** (a regex pattern) to mutated strings with names, levels and locations; the instrumenter keeps the Babel AST, placement, ids and reporting. A UI library fits the same split for **template sub-languages that the instrumenter treats as strings or does not parse**: Angular template strings, Vue `<template>` blocks, CSS declarations, HTML. Example shape: `mutateAngularTemplate(source, options) -> { replacementSource, name, description, location, levels }[]`. Levels map naturally onto the P1/P2/P3 priorities above.
- It does **not** fit JSX: JSX is already part of the Babel AST, so a JSX operator is a `NodeMutator`, and the hard part is placement (F.1), which must stay inside the instrumenter. An external package could still own the "which attribute/text is worth mutating" rules (attribute allow-lists, ARIA state names, role tables) as data or pure predicates.
- **Upstream change needed** to plug in the way weapon-regex does: a delegating mutator must be compiled into the instrumenter (as `Regex` is) and the dependency added to its `package.json`, i.e. a PR to `@stryker-mutator/instrumenter`. For JSX: one new mutator file per operator family plus the JSX-aware placement fix from F.1 (the child/attribute wrapping is needed by any JSX-element-level mutant). For templates and CSS the change is larger than weapon-regex ever needed: the regex mutator rides on an existing JS node, while Angular/Vue templates and CSS need a new parser/transformer/printer entry in `create-parser.ts`/transformers/printers and a runtime switch that template code can reach (#5156). Also, the StrykerJS side would want to keep the library's `name`/`description` instead of collapsing them into one mutator name, which `regex-mutator.ts` does today; mutator naming per sub-mutator would need either many `NodeMutator` names or a schema change (reports only carry `mutatorName`).
- Without upstream changes, the same delegation works from a plugin through routes b-1 (JSX, Babel-level) and b-2 (new formats), with the package boundary identical: the plugin is the "instrumenter side", the operator library the "weapon-regex side".
- Publishing: if the library is TypeScript (this repo's stack), the weapon-regex Scala.js packaging steps do not apply; what transfers is the API discipline (versioned `Mutant` record with `location`, levels, a `byName`/`byLevel` registry, a stable `mutate()` entry point, and compatibility checks that ignore internals).
