### 1.1 JavaScript: StrykerJS and friends

Sources for this subsection were collected by a research worker and spot-checked by Claude (jp-photo-manager support file, stryker-js#6238, stryker-js#3856 re-opened through `gh`). Local StrykerJS citations are at tag `v10.1.1` in `D:/projects/github/stryker-mutator/stryker-js`.

**Official runners that drive a real browser**

- `@stryker-mutator/karma-runner` has run mutants in real browsers since before vitest browser mode, and it is the closest existing shape to a Playwright runner. Mechanics [checked: `packages/karma-runner/src/karma-test-runner.ts`, `karma-plugins/stryker-reporter.ts`, `karma-plugins/test-hooks-middleware.ts`, `karma-plugins/stryker-mutant-coverage-adapter.ts`, `karma-plugins/stryker-karma.conf.ts`]:
  - A virtual `test-hooks-middleware-<uuid>.js` file is put first in Karma `files` (`served: false, nocache: true`) and served by an Express `beforeMiddleware` with `Cache-Control: no-cache`. Before each run its body is rewritten in memory: for a perTest dry run it installs a jasmine `specStarted` / mocha `beforeEach` hook that writes `window.__stryker__.currentTestId`; for a mutant run it writes `window.__stryker__.activeMutant = "<id>"`, `hitCount = 0`, `hitLimit = <n>` and a test filter (`jasmine.getEnv().configure({specFilter})` or `mocha.grep`). Because the hooks file runs before the SUT on every iframe load, the runner ignores `mutantActivation` entirely and reports `reloadEnvironment: true`.
  - Coverage comes back by wrapping `window.__karma__.complete` in the browser and attaching `__stryker__.mutantCoverage` and `hitCount` to the complete payload; the Node-side reporter stores them in `onBrowserComplete` and applies `determineHitLimitReached`.
  - One Karma server and one captured browser per Stryker worker, started in `init()`; each run is `karma.runner.run()` against the live server. Forced options: `autoWatch: false`, `singleRun: false`, `browserNoActivityTimeout: 1000000` (comment: default 10 s "might not enough to send perTest coverage results"), `clearContext: false` (race, stryker-js#2049), jasmine `random: false` (stable spec ids), fail-fast/bail unless `disableBail`.
  - A DISCONNECTED browser is restarted through the launcher and the pending run resolves as Timeout ("Browser disconnected during test execution"). The origin is stryker-js#356 (2017): an infinite-loop mutant disconnected the browser and marked all remaining mutants Survived. [checked: `gh issue view 356` title/body by the worker]
  - Limits in `docs/karma-runner.md`: lifecycle options are non-overridable, perTest coverage only for jasmine and mocha, `--testFiles` unsupported.
- `@stryker-mutator/vitest-runner` browser mode: see the prior report (`RESEARCH.md` section 1); not repeated.

**Core planning facts a browser runner inherits** [checked: `packages/core/src/mutants/mutant-test-planner.ts` L88-137, L169-219; `packages/core/src/test-runner/reload-environment-decorator.ts` L17-72; `packages/core/src/process/4-mutation-test-executor.ts` L255-275; `packages/api/src/test-runner/run-options.ts`]

- `isStatic = hasStaticCoverage(id)` (hit while no `currentTestId` was set, i.e. module-load code). Non-static covered mutants run only `coveredBy` tests; static mutants run all tests (or are Ignored with `ignoreStatic`); with `coverageAnalysis: "off"` everything runs all tests.
- `canHotSwap = !!testFilter && isStatic === false`; `mutantActivation = testFilter ? 'runtime' : 'static'`; `reloadEnvironment = !canHotSwap`. Runs that need a reload are sorted last (stryker-js#3462). The decorator tracks Pristine / Loaded / LoadedStaticMutant and calls `recover()` (kill and restart the worker) when a runner cannot reload.
- `timeout = timeoutFactor * netTime + timeoutMS + overhead`; `hitLimit = dryRunHitCount * 100`.
- `toMutantRunResult()` in `packages/api/src/test-runner/run-result-helpers.ts` L20-67 returns **Survived for an empty `tests` array**. Open issues stryker-js#6213 ("mutants with testsCompleted: 0 are reported as Survived") and #6256 (no test reaches any mutant -> Survived instead of NoCoverage) and the closed #6255 (mutant throwing at import -> Survived, fixed) show this is a recurring false-survivor source. [checked by the worker: titles; helper code read]
- Consequence [inferred]: a Playwright runner that reports no coverage makes every mutant static + reload. One that reports perTest coverage gets runtime activation and filtered test lists for most mutants, and only module-scope mutants need a page load with the mutant already active. Since every e2e test calls `page.goto` anyway, the page reload is cheap; the expensive part is any dev-server or bundle cache that spans mutants.

**Community command-runner bridges into a browser**

**Other JavaScript mutation tools** [checked by the worker: registry entries at `registry.npmjs.org`, repos via `gh api`]

- Mutode (`TheSoftwareDesignLab/mutode`, last publish 2018, repo last push 2020): copies the project into `.mutode/mutode-<id>-<i>` directories, writes each mutated file to disk and runs `npm test` in the copy, timeout derived from the clean run. No browser or e2e support; dormant.
- grunt-mutation-testing (Stryker's predecessor, 2016): default `testFramework: "karma"`, a pool of up to `maxActiveServers` (default 5) Karma servers "on ports subsequent to the configured Karma port", `waitForRunnerTime` 2 s per run to detect infinite loops, with the README warning it "may trigger false positives". The earliest written record of the per-worker-port and fixed-timeout-false-kill lessons.
- Test-side mutation for Playwright (mutate the test, not the SUT): `playwright-mutation-gate` (0.3.3, 2026-07) and `apophasis` (1.0.5, 2026-03) invert assertions and re-run; apophasis's `--baseline` note: results "may be unreliable if your test suite is broken or flaky". Complementary; they have no activation or server problem.
- `testguard-cli` (0.20.1, 2026-09, `raccioly/testguard`): claim-driven fault injection with a Playwright "defender" runner. Reads results from the JSON reporter through `PLAYWRIGHT_JSON_OUTPUT_FILE`, never stdout; status mapping: `flaky` (passed on retry) is "NOT green", `timedOut` is "never a kill". Discovery via `playwright test --list --reporter=json`.
- `@systemfsoftware/stryker-js` (fork) README says a Vitest config with browser mode enabled "is refused". Nothing else on npm (`stryker playwright`, `mutation playwright`, `stryker runner`, `stryker cypress`, `keywords:stryker-plugin`, `mutation e2e`) targets a browser e2e tool; third-party Stryker runners found are Bun (two), Overkill, lab (2017) and `stryker-mutator-rust`.

Details worth keeping:

- **Stryker.NET MTP runner is the only tool that switches a reused process and collects per-test coverage from it without an in-process hook**: a memory-mapped file for the id (read per call because the reused host "has no per-run reset hook"), coverage files named from `STRYKER_COVERAGE_FILE`, and an epoch file the runner bumps to say "test N finished, flush now" and waits for an ack. Issue #3915 (open) reports `IsActive` contention on the mapped view slowing mutated code into timeouts: the per-call read has a cost. [checked]
- **mutmut's `MUTANT_UNDER_TEST=fail` mode** makes every mutant raise, to prove the switch actually reaches the code. Muter #307 (open) is the failure it guards against: schemata "silently never applied", so every run tested unmutated code and reported survivors, found only by running `strings` on the build output. [checked]
- **mutmut #474**: a user replaced fork-per-mutant with N long-lived workers that each loop over mutants and call `pytest.main()` repeatedly with a different `MUTANT_UNDER_TEST`, cutting a 938-mutant run from ~2 h to ~14 min, because the trampoline re-reads the env var per call; the parent must hold no live connections when forking. **#545**: a DB-bound suite produced 616 timeouts at default parallelism versus 366 at `--max-children 2`, and cached timeout verdicts replay on resume. **#584**: process pools started by tests outlived every mutant; one run orphaned 8,359 processes and used 120 GB RAM. [checked]
- **PIT FAQ**: classloading order under mutation makes millisecond tests take seconds, causing false timeouts; the remedy is a larger `timeoutConst`; a timeout costs a new JVM. **#827** (Testcontainers): shared DB state persisted between mutants; hcoles: "This is one of the reasons (along with performance) that mutation testing with integration tests is not usually reccomended". [checked]
- **Infection #1671**: parallel runs reported 100% MSI because tests failed for environment reasons (Docker file permissions), not because of the mutant; the maintainer attributes a higher MSI in parallel to tests "being conflicted with each other". A false-kill signature worth a guard. [checked]
- **Mutant (Ruby)**: `coverage_criteria.timeout: false` by default, so timeouts do not count as kills; worker `index:` is passed to `mutation_worker_process_start` hooks for per-worker databases. [checked]
- **METFORD** restarted the emulator never / before each mutant / before each test (scripts offered for all three) and only restarted when the emulator became unavailable; flakiness was handled before mutation by running each instrumented test 10 times on 8 emulators and `@Ignore`-ing unstable ones. [checked]
- **grunt-mutation-testing** (JS, 2016) already ran a pool of up to 5 Karma servers on consecutive ports with a fixed 2 s per-run wait that the README admitted "may trigger false positives". [checked, section 1.1]

Cross-tool patterns [inferred from the checked rows]:

1. Activation that crosses a process boundary is always an inheritable or global channel: env vars (mull, mutmut, Stryker4s, go-mutesting, Muter), a device property (METFORD), the file system (mutatest, rebuild-based tools) or a memory-mapped file (Stryker.NET MTP). In-process mechanisms (PIT hot swap, Mutant monkeypatch, Infection stream wrapper, Major config class) cannot reach a separately started server.
2. Per-test coverage, where it exists, is collected inside the test process. Only Stryker.NET's file-based MTP coverage and mull's profraw output are channels a child process could feed, and neither documents that.
3. Every tool with a documented separate-process story runs the whole test command per mutant.
4. Shared external state is the common failure; per-worker tokens (Infection `TEST_TOKEN`, Mutant `index:`) are the standard fix, and timeouts inflate under parallel contention everywhere (mutmut, gremlins, cargo-mutants, mutatest, PIT).

### 2.1 Web-specific mutation operators and tools

- **Mutandis** -- Mirshokraie, Mesbah, Pattabiraman, "Efficient JavaScript Mutation Testing", ICST 2013 (doi:10.1109/icst.2013.23) and "Guided Mutation Testing for JavaScript Web Applications", IEEE TSE 41(5) 2015 (doi:10.1109/tse.2014.2371458). Static and dynamic analysis aim mutants at error-prone code; a FunctionRank metric picks variables and branches; >93% of mutants non-equivalent; >75% of surviving non-equivalent mutants are in the top 30% of ranked functions. Repo `saltlab/mutandis`. [checked, abstract only; the PDF host blocks automated access, so the operator list and how mutants ran against the DOM are **not verified**]
- **webMuJava** -- Praphamontripong and Offutt, "Applying Mutation Testing to Web Applications", ICSTW/Mutation 2010 (doi:10.1109/icstw.2010.38): web mutation framed as _integration_ testing of client-server and server-server interactions; new operators on JSP/servlet links, forms, sessions. Praphamontripong, Offutt, Deng, Gu, "An Experimental Evaluation of Web Mutation Operators", ICSTW 2016 (doi:10.1109/icstw.2016.17): 11 apps, 15 operators, 12 independently written test sets; tests built for traditional criteria killed **47% of web mutants on average**, some easy web mutants were missed by every traditional set, and web mutation "produces very few equivalent mutants". Praphamontripong and Offutt, ICSTW 2017 (doi:10.1109/icstw.2017.30): three operators (WFUR, WHID, WLUD) are redundant. [checked, abstract only]
- **MaewU** -- Yandrapally and Mesbah, "Mutation Analysis for Assessing End-to-End Web Tests", ICSME 2021 (doi:10.1109/icsme52107.2021.00023). Mutates **the live DOM in the browser instead of source code**, so it is stack-agnostic; 16 operators on behaviour and appearance of elements, covering nine fault categories mined from 250 bug reports; evaluated on six open-source apps against Selenium-style suites. [checked, abstract only]. Relevance [inferred]: this is the only published tool whose "activation" is a browser-side DOM patch; it sidesteps servers, builds and realms entirely, but it measures the test suite's oracle strength rather than its coverage of application logic, so it complements rather than replaces source mutation.
- **Mutta** -- Leotta, Paparella, Ricca, "Mutta: a novel tool for E2E web mutation testing", Software Quality Journal 32:5-26 (online 2023, issue 2024, doi:10.1007/s11219-023-09616-6). [checked, full text; tool repo https://github.com/DavidKipe/mutta, checked by the other worker]
  - Pitest generates mutants of the **server-side Java**; for each one Mutta patches the source, redeploys the app, runs the whole Selenium WebDriver suite, saves results, restores the original. A "coverage with prints" mode first inserts a print of the mutant id instead of the mutation to learn which mutants the e2e suite reaches.
  - **Coverage filter is essential.** E2E coverage of mutants: Petclinic 98/107 (91.6%); Shopizer only **1882 of 15k generated (12.5%)**. Without the filter, uncovered mutants count as survived.
  - **Cost.** "Several minutes" per mutant. Petclinic: 31 tests x 98 mutants, about 6 h. Shopizer: 53 tests x 1882 mutants, **estimated 220 h per suite**; a cap of 3 mutants per Java method cut it to 491 mutants, still ~62 h, then sharded across 10 VirtualBox VMs (~50 mutants, ~6 h each). About 87k test runs in the study.
  - **Kill rates.** Petclinic: assertion suite 82%, Recheck explicit differential 90%, implicit 91%. Shopizer: 39%, 51%, 52%. Oracle style moves the score by up to 13 points.
- **Not found** (queries recorded in the part file): CSS or HTML mutation operators; Angular/React/Vue-specific operators; a Cucumber/BDD mutation paper; an Espresso-specific mutation paper. Nearest: Silva, Vergilio, Endo, "Accessibility Mutation Testing of Android Applications", JSERD 2022 (operators negate WCAG criteria). [checked, abstract only]

### 2.2 GUI and mobile

- Oliveira, Alégroth, Gao, Memon, ICSTW 2015 (doi:10.1109/icstw.2015.7107457): 18 GUI-level operators; method-level operators are "not precise enough" for GUI faults. [abstract only]
- Deng, Mirzaei, Ammann, Offutt, "Towards mutation analysis of Android apps", ICSTW 2015 (doi:10.1109/icstw.2015.7107450): installs and executes each mutant on Android; names "running Android tests is slow" as the challenge. Follow-ups: IST 2017, QRS 2017 (effective against real and crowdsourced faults), SEKE 2018 (three redundant operators, subsumption relations). [abstract only]
- **MDroid+** -- Linares-Vásquez et al., "Enabling Mutation Testing for Android Apps", ESEC/FSE 2017 (doi:10.1145/3106237.3106275, arXiv:1707.09038). 38 operators from a taxonomy of 262 fault types; an Execution Engine ran **20 concurrent x86 emulators** launching every mutant APK; stillborn rates MDroid+ 0.56%, Major 1.8%, muDroid 53.9%, PIT 0%; trivial (crash-on-launch) rates 2.42% / 5.4% / 11.8% / 7.2%. Equivalent mutants were not studied because the subject apps had no test suites. [checked, full text]
- µDroid -- Jabbarvand and Malek, ESEC/FSE 2017 (doi:10.1145/3106237.3106244): 50 energy operators and an **automatic oracle** deciding kill/survive with 94% accuracy. [abstract only]
- METFORD -- Vincenzi et al., arXiv 2025 (doi:10.48550/arxiv.2501.02875): schemata for Android in one APK; versus one APK per mutant, 8.50% less generation time, 99.78% less disk, 6.45% faster execution; instrumented test suites killed 15.6% of mutants on average (section 1.2). [full text read by the other worker; abstract by this one]

### 2.3 Cost reduction relevant to slow suites

- **Schemata**: Untch, Offutt, Harrold, ISSTA 1993 (doi:10.1145/154183.154265), one metaprogram compiled once, "over 300%" speedup. This is what StrykerJS, Stryker.NET, Stryker4s, mutmut 3, mull, Muter, Major and METFORD do. [abstract only]
- **Split-stream / fork / state equivalence**: MuVM (Tokumoto et al., ICST 2016, doi:10.1109/icst.2016.18), AccMut (Wang et al., ISSTA 2017, doi:10.1145/3092703.3092714, **2.56x** over split-stream on 337k mutants, full text), infected-state partitioning (Just, Ernst, Fraser, ISSTA 2014, doi:10.1145/2610384.2610388, **-40% time**). [inferred] All assume one process whose state can be forked at the mutation point; a browser + app server + test worker topology has no such point, so these do not transfer.
- **Per-test coverage for selection**: Javalanche (Schuler, Zeller, ESEC/FSE 2009), Major (Just, ISSTA 2014), PIT (Coles et al., ISSTA 2016). Google (Petrović, Ivanković, ICSE-SEIP 2018; with Fraser and Just, IEEE TSE 2021, doi:10.1109/tse.2021.3107634, full text): line coverage is a prerequisite, mapping each line to "the minimal set of tests that need to be run in an attempt to kill a mutant"; mutants only on changed and covered lines, **at most one per line**, arid nodes excluded; all mutants evaluated in parallel on their own temporary VCS state; surviving mutants shown capped at 7 x files changed; the 2018 paper notes "about 15% of coverage statement calculations fail". The TSE 2021 paper says nothing about flaky tests (full-text search for "flak").
- **Ordering tests**: Just, Kapfhammer, Schweiggert, ISSRE 2012 (doi:10.1109/issre.2012.31): ordering tests by runtime and mutation coverage plus suite splitting cut cost "as much as 65%" on 400 KLOC / 550k mutants; non-redundant COR/ROR operators cut mutants up to 37%. Zhang, Marinov, Khurshid, ISSTA 2013 (doi:10.1145/2483760.2483782): prioritise and reduce tests per mutant to reach verdicts faster. Regression mutation testing (Zhang et al., ISSTA 2012). [abstract only]
- **Prediction and sampling**: Predictive Mutation Testing (Zhang et al., ISSTA 2016; TSE 2018, doi:10.1109/tse.2018.2809496): classifier predicts kill/survive without execution, up to 151.4x faster, AUC >0.80 on most of 163 projects; MutationBERT (Jain et al., ESEC/FSE 2023) saves 33% of live-mutant checking. Selective mutation (Offutt et al., TOSEM 1996) cuts mutants by an order of magnitude. Higher-order mutation (Jia, Harman, IST 2009) and the Papadakis et al. survey (2019): metadata only. [abstract only or metadata]
- **Incremental**: Cachia, Micallef, Colombo, ENTCS 2013 (mutate only changed code); ReMT. [abstract only]
- **Facebook** -- Beller et al., "What It Would Take to Use Mutation Testing in Industry", ICSE-SEIP 2021 (doi:10.1109/icse-seip52600.2021.00036, arXiv:2010.13464). [checked, full text]
  - Runs unit, integration **and end-to-end** tests per diff through ML predictive test selection (>=99% chance of including a catching test).
  - Mutant diffs run **off-peak, 7 p.m. to 7 a.m. Pacific**: "hundreds to thousands of mutants per day without incurring noticeable infrastructure cost".
  - **A logging statement is inserted into each mutant, so a failing test counts as a kill only if it actually executed the mutated code**; persistently flaky tests are disabled.
  - More than half of >15,000 mutants survived the combined suites; a developer: "I'm a bit disappointed that our e2e tests didn't catch that."

### 2.4 e2e / system suites versus unit suites

**No controlled comparison of unit versus e2e mutation score on the same code was found** (OpenAlex and arXiv queries listed in the part file; Trautsch, Herbold, Grabowski, JSS 2020, doi:10.1016/j.jss.2019.110421, could not be checked for mutation use). Indirect evidence [checked as marked above]:

- Web interaction mutants: traditional tests kill 47% on average (Praphamontripong 2016).
- Mutta: e2e suites reach only 12.5% of server mutants on a realistic app and 91.6% on a toy; on reached mutants, 39-52% (Shopizer) versus 82-91% (Petclinic); the oracle style matters as much as 13 points.
- Facebook: >50% of mutants survive unit + integration + e2e combined.
- Android: Deng et al. report mutation effective at exposing real faults; MDroid+ trivial rates 2.4-11.8% are the GUI analogue of "killed by every test".
- Equivalent mutants: web operators "produce very few"; Mutandis >93% non-equivalent. No subsumption study at e2e level.
- Oracle data selection (Gay, Staats, Whalen, Heimdahl, TSE 2015) shows oracle choice substantially changes fault finding; [inferred] e2e tests observe only the rendered UI, so weak assertions are the likely cause of low e2e kill rates rather than reachability alone.

## 3. Mechanics

### 3.1 Mutant schemata ("mutation switching") is the baseline that makes e2e feasible at all

- StrykerJS 4.0 (beta announced 2020) replaced copy-per-mutant with **mutation switching**: every mutant is compiled into the code once, guarded by `global.activeMutant === <id>` checks, so a bundler or compiler runs once and the test runner is re-run per mutant with a different active id. The blog gives the `add(a, b)` example and names the motivation: "when you bundle your code with webpack before running the tests, then webpack only needs to run once." [checked: https://stryker-mutator.io/blog/announcing-stryker-4-beta-mutation-switching/]
- The same post introduced `buildCommand` (build once, any tool) and dropped transpiler plugins. [checked: same post]
- PR stryker-js#2345 (merged 2020-08-03) made the `command` runner work with switching by exporting `__STRYKER_ACTIVE_MUTANT__` into the child environment. nicojs's note in the PR body: support is "best effort", it "only works if the command you configure allows for this environment variable to flow through to the test environment", so it works for Node runners (tap, mocha) "but not for test runners that spin up their own test environment, like jest or karma." A browser is such an environment. [checked: https://github.com/stryker-mutator/stryker-js/pull/2345]
- `docs/configuration.md` at v10.1.1: the command runner "can be made to work in any use case, but comes with a performance penalty, as Stryker cannot do any optimizations and just runs all tests for all mutants." [checked: `git show v10.1.1:docs/configuration.md`, lines 549-553 in the local clone `D:/projects/github/stryker-mutator/stryker-js`]

### 3.2 Collecting a per-test global out of a browser page (prior art from Istanbul coverage in Playwright)

- `mxschmitt/playwright-test-coverage` (143 stars, pushed 2026-05-24; "Playwright Test demo to collect coverage information via Istanbul") solves the same problem a Stryker runner has, with `__coverage__` instead of `__stryker__.mutantCoverage`. Its `e2e/baseFixtures.ts` overrides the `context` fixture to: (1) `context.addInitScript` a `beforeunload` listener that calls an exposed function with `JSON.stringify(window.__coverage__)`, so coverage survives **navigations** (each full page load starts with a fresh global); (2) `context.exposeFunction('collectIstanbulCoverage', ...)` writing a JSON file per flush; (3) after `use(context)`, `page.evaluate` the same flush for every still-open page. [checked: https://github.com/mxschmitt/playwright-test-coverage, file `e2e/baseFixtures.ts` read through `gh api`]
- Relevance [inferred]: a Stryker Playwright runner cannot read `__stryker__` once per test with a single `page.evaluate`, because an e2e test typically navigates several times and may open several pages; every navigation drops the in-page `mutantCoverage` and `hitCount`. The `beforeunload` flush + `exposeFunction` pattern, merged per test, is the minimal fix. The fixture also shows where the merge key (test id) must be injected: in the same `addInitScript`, read from the worker process.
- Playwright's native `page.coverage` (V8 coverage, `startJSCoverage`/`stopJSCoverage`) is Chromium-only. It could map tests to source files without Stryker instrumentation, but it does not produce Stryker's mutant-id coverage, so it is only useful for a coarse "which files does this test load" filter. [checked: `git show v1.64.1:docs/src/api/class-coverage.md` in `D:/projects/github/microsoft/playwright`, note "Coverage APIs are only supported on Chromium-based browsers"; the mapping remark is inferred]

- `cypress-io/code-coverage` (441 stars, pushed 2026-10-24) is the Cypress analogue and adds two things [checked: `lib/support.ts` and `middleware/express.ts` read through `gh api`, https://github.com/cypress-io/code-coverage]:
  - **Per-test, multi-navigation capture.** In `beforeEach` it registers `cy.on('window:load', saveCoverageObject)` so every page load during a test contributes its `win.__coverage__` reference (de-duplicated per window, refreshed when the user "navigates away and then returns to the page, in which case we need to use new applicationSourceCoverage, because the old will not be updated anymore"). Cross-origin windows throw on access and are skipped. `afterEach` sends the collected objects. Playwright's equivalent hook is `page.on('load')` or `page.on('framenavigated')`, or the `beforeunload` flush above. [checked, lines 102-160 of `lib/support.ts`]
  - **Server-side coverage over HTTP.** In e2e mode the plugin `cy.request`s `GET /__coverage__` (configurable `codeCoverage.url`) and expects `{ coverage }` from an app-side middleware that returns `global.__coverage__`. Express/Hapi/Next.js middlewares are shipped. [checked: `middleware/express.ts`]
  - Relevance [inferred]: a Stryker runner can expose `globalThis.__stryker__` of an SSR or API server the same way (a tiny route or a sidecar HTTP endpoint added by a Stryker-only preload) and merge it with the browser-side object per test, which gives per-test coverage for server-side mutants without a per-mutant restart. Activation on the server still needs a switch the server reads (env at start, or a mutable in-process value settable by the same endpoint).

### 3.3 The Stryker switch is a live read, so a running server can change mutant without a restart

From the instrumenter prelude at v10.1.1 [checked: `git show v10.1.1:packages/instrumenter/src/util/syntax-helpers.ts`, `instrumentationBabelHeader`, lines 21-70 in the local clone]:

- `stryNS_9fa48()` resolves `globalThis` (core-js style) and creates `g.__stryker__` once per **JS realm**. Every page, iframe, web worker, service worker and Node process has its own namespace. [checked]
- The env fallback runs **once**, only while `ns.activeMutant === undefined`: `if (ns.activeMutant === undefined && g.process && g.process.env && g.process.env.__STRYKER_ACTIVE_MUTANT__) ns.activeMutant = ...`. So an env var seeds the value; it does not pin it. [checked]
- `stryMutAct_9fa48(id)` compares `ns.activeMutant === id` **on every evaluation** and bumps `ns.hitCount` against `ns.hitLimit`, throwing `'Stryker: Hit count limit reached'` when exceeded. There is no caching of the active id in the mutated code. [checked]
- `stryCov_9fa48(...)` writes to `cov.perTest[ns.currentTestId]` when `currentTestId` is set, else `cov.static`, also read live per call. [checked]

Consequences [inferred from the checked code]:

1. A long-lived SSR or API server built from the instrumented tree can be switched between mutants by assigning `globalThis.__stryker__.activeMutant` at runtime (for instance through a Stryker-only HTTP route, or a `--require`/`--import` preload that polls a file or listens on a socket). Only the first activation needs a process start; module-level (static) mutants that ran during import stay baked in and need a restart, which is exactly Stryker's static/runtime `mutantActivation` distinction.
2. In the browser the same holds per page: `page.addInitScript` must set `__stryker__.activeMutant` and `__stryker__.currentTestId` **before any instrumented module runs**, on every navigation, in every frame and worker that loads instrumented code. The `addInitScript` docs list only "whenever the page is navigated" and "whenever the child frame is attached or navigated" (page and context variants) [checked: `git show v1.64.1:docs/src/api/class-page.md` lines 566-576 and `class-browsercontext.md` lines 383-393], so web workers and service workers are not covered and instrumented code there needs another carrier (a `define` baked at build time, a query parameter read by a tiny bootstrap, or `localStorage`/`BroadcastChannel`).
3. Because `hitCount`/`hitLimit` are per realm, a page that navigates mid-test resets the hit counter; an infinite loop introduced by a mutant in a browser is caught by Playwright's test timeout rather than by the hit limit unless the limit is re-seeded in `addInitScript`.

## 5. Flakiness and mutation scores

### 5.1 Measured effect sizes

- **Shi, Bell, Marinov, "Mitigating the Effects of Flaky Tests on Mutation Testing", ISSTA 2019** (doi:10.1145/3293882.3330568). [checked, full text; Claude re-read the converted PDF for the numbers] Mutation scores vary by **4 percentage points on average** between repeated runs of the same suite; **9% of mutant-test executions and about 4% of mutants** have "unknown" status, meaning the test did not reach the mutated code on that run even though earlier coverage said it would, so its failure is no evidence of a kill. Mechanisms, implemented in PIT: (1) stable coverage from 16 runs, union of covered blocks; (2) rerun a test on a mutant **until it covers the mutant, up to 16 times**; (3) **escalate isolation** (shared JVM -> JVM per test class -> JVM per mutant-test pair, up to 5 reruns per level); (4) prioritise tests by how reliably they cover the mutant. Result: unknown mutants down **79.4%**; the first rerun recovers most pairs; changing isolation helped more than extra reruns; a JVM per mutant-test pair ran **52x slower**. Among rerun pairs: 38.0% always killed, 29.7% always survived, 32.3% mixed.
- **FlakiMe** -- Cordy, Rwemalika, Papadakis, Harman, arXiv:1912.03197 (2019, full text) and with Franci, ICSE 2022 (doi:10.1145/3510003.3510194, abstract). Seeds a fixed failure probability per passing test. At p=0.05 the mutation score is inflated by a median of 1.76% (Commons Lang) to 4.87% (JFreeChart); at the highest tested probability JFreeChart rises from 33.12% to 49.71% and Commons Lang from 83.35% to 91.51%. ICSE abstract: 10% flakiness gives a modest 2-5% effect. So **flakiness inflates the score (false kills) and hurts low-score suites most** [the last clause inferred from the numbers].
- **Test Flimsiness** -- Parry, Kapfhammer, Hilton, McMinn, ICSE 2026 (doi:10.1145/3744916.3773125, abstract): **mutations themselves can make tests flaky**, a second threat separate from pre-existing flaky tests. [inferred] In e2e this is the common case: a mutant that slows a request, removes a `await`-ed state transition, or changes a timeout turns a stable test into a timing-dependent one.
- E2E flakiness baseline, not mutation-specific: WEFix (Liu et al., WWW 2024) generates explicit waits for UI flakiness; de Moura et al., SBES 2024: up to 32% of a Cypress suite can break on synchronisation issues. [abstract only]
- Not found: a majority-vote or "flaky-aware mutation score" formula beyond Shi's "unknown" status (queries in the part file).

### 5.3 What this means for scoring an e2e run [inferred]

- False kills come from three sources: pre-existing flaky tests (FlakiMe: +2-5 points at 5-10% flakiness), mutation-induced flakiness (flimsiness), and environment failures (ports, caches, leaked processes). False survivors come from the mutant not being active in the realm under test, from `testsCompleted: 0` mapping to Survived, from uncovered mutants without a coverage filter, and from cached bundles.
- The cheapest high-value guard is Facebook's and Shi's: **accept a kill only when the mutant's hit count is > 0 in the failing test's run**, which Stryker already has as `hitCount` per realm once it is carried back from the page. The second is a Playwright-native rerun (`retries`) interpreted the testguard way: a pass-on-retry is not a kill and not a survival but an "unknown" worth a rerun under stronger isolation (fresh context, fresh server).

## 6. Ideas worth taking for a Playwright runner

Ranked by expected value for the prototype: (score gain or run-time saved) x (confidence it transfers) / (effort). Each item names its source section. The ranking itself is [inferred]; the mechanisms are [checked] where the section says so.

1. **Report per-test coverage from the page, or every mutant is static and runs the whole suite.** Core plans `canHotSwap = testFilter && !isStatic`; no coverage means `reloadEnvironment: true` and all tests for every mutant (section 1.1). Mutta measured what that costs: 220 h for one app, and e2e suites reach only 12.5% of server mutants on a realistic app, so the coverage filter alone removes most of the work (section 2.1). Facebook and Google both make coverage a prerequisite (section 2.3). Mechanism: set `__stryker__.currentTestId` in `addInitScript` per test, flush `__stryker__.mutantCoverage` on `beforeunload` through `exposeFunction` and once more in fixture teardown, merge per test (section 3.2). This is the single feature that separates a runner plugin from the `command` runner.
2. **Accept a kill only when the mutant was hit in that run.** Facebook logs inside each mutant for exactly this; Shi 2019 cut "unknown" verdicts 79.4% with coverage-confirmed reruns (sections 2.3, 5.1). Stryker's `hitCount` already exists per realm; carry it back with the coverage object and treat "test failed, hitCount 0" as unknown, not Killed. Cheap, and it neutralises most e2e false kills.
3. **Flush the page global on every navigation, in every frame, and seed it in every realm.** The instrumenter namespace is per realm and the env fallback runs once (section 3.3); `addInitScript` covers pages and frames only (section 3.3). `playwright-test-coverage` and `cypress-io/code-coverage` already solve the navigation and multi-window cases for Istanbul (section 3.2). The karma-runner's no-cache, first-in-order hooks script is the same idea (section 1.1). Not doing this is the uniform-0%-score failure in jp-photo-manager and stryker-js#6238 (sections 1.1, 5.2).
4. **Add a self-check that the switch reaches the code before reporting survivors.** mutmut's `MUTANT_UNDER_TEST=fail`; Muter #307 shipped unmutated builds silently; jp-photo-manager confirmed a stuck 0% "empirically" (sections 1.2, 5.2). In Stryker terms: after the dry run, assert that `mutantCoverage` is non-empty for at least one test, and fail init with a clear message otherwise (stryker-js#6256 asks for the NoCoverage path to exist).
5. **Keep the server alive and switch the mutant at runtime; restart only for static mutants.** The switch is a live read, so an SSR or API server can be re-pointed by assigning `globalThis.__stryker__.activeMutant` (section 3.3). Stryker.NET's MTP runner is the worked precedent for a reused process: memory-mapped id + file-based coverage + epoch handshake (section 1.2). mutmut #474: long-lived workers looping over mutants took a 938-mutant run from ~2 h to ~14 min (section 1.2). Expose a Stryker-only HTTP route (the `cypress-io/code-coverage` `/__coverage__` middleware shape, section 3.2) that sets the active mutant and returns the server's `__stryker__` object; let core's `reloadEnvironment` flag drive the restart for static mutants only.
6. **Per-worker ports and cache dirs, never shared.** nxtcm-components (per-mutant port and CT cache dir, "the main cause of false 'survived' results"), grunt-mutation-testing (consecutive Karma ports), Infection `TEST_TOKEN`, Mutant `index:` (sections 1.1, 1.2, 4). Derive the port from the Stryker worker id and pass it into the Playwright config through env; set `reuseExistingServer: false` per worker, not per mutant.
7. **Map Playwright statuses the testguard way.** `flaky` (passed on retry) is not green; `timedOut` is never a kill; read the JSON reporter output from a file, never stdout (section 1.1). Mutant (Ruby) defaults timeouts to not-a-kill (section 1.2). Combine with Stryker's own timeout and `hitLimit` (re-seed `hitLimit` in `addInitScript`, section 3.3).
8. **Restart the browser on disconnect and report Timeout for that mutant.** karma-runner's `onBrowserError` path exists because stryker-js#356 marked all later mutants Survived after one infinite loop (section 1.1). With Playwright: a crashed context or `webServer` should resolve the current `mutantRun` as Timeout and recreate the context before the next run.
9. **Order and bound the work before running it.** Google: one mutant per line, changed and covered lines only; Mutta: cap mutants per method; Just et al.: order tests by runtime and coverage for up to 65% less cost (section 2.3). In Stryker terms: recommend `mutate` ranges, `ignoreStatic`, and sort each mutant's `testFilter` by dry-run duration so the fastest killer runs first under `bail`.
10. **Treat parallel contention as a timeout source, not a speedup.** mutmut #545 (616 -> 366 timeouts by halving workers), gremlins, cargo-mutants, mutatest and the PIT FAQ all report it (sections 1.2, 5.2). Default `concurrency` to RAM-bound browsers plus servers (nxtcm capped at 4), and document that a rising Timeout count means fewer workers, not a bigger `timeoutFactor`.
11. **Run the baseline first and refuse a red or flaky one.** Stryker's dry run does this; keep `break-on-initial-test-failure` semantics and run the dry run with `retries: 0` so flaky tests surface before they inflate the score (FlakiMe: +2-5 points at 5-10% flakiness; section 5.1).
12. **Later: DOM-level mutation as a second mode.** MaewU mutates the live DOM in the browser, stack-agnostic, to measure oracle strength (section 2.1). A Playwright fixture could inject the same 16 operators without any Stryker instrumentation. Out of scope for a Stryker runner but the cheapest way to measure e2e assertion quality.

## 7. Known dead ends

Each entry says who hit it and where it is recorded.

- **Relying on the `command` runner's env var for browser code.** The instrumented check only reads `process.env` in a realm that has `process`; a page never does. Every mutant survives, the score sits at ~0% (jp-photo-manager comment, cypress#16299, stryker-js#6238; PR #2345's own "best effort" note). Sections 1.1, 3.1, 3.3. [checked]
- **Running the whole e2e suite per mutant.** 450 Cypress CT tests at 15 min a run exceeded a 6 h CI limit even with incremental mode (stryker-js#3856); Mutta estimated 220 h for one app; the generic advice online is to exclude e2e from mutation entirely (qaskills.sh). Sections 1.1, 2.1, 4. [checked]
- **Reusing a dev-server bundle or CT cache across mutants.** nxtcm-components names it "the main cause of false 'survived' results"; the hello-world demo pays a server restart per mutant instead. Section 4 and `RESEARCH.md`. [checked]
- **Mapping an empty test run to Survived.** `toMutantRunResult` returns Survived for an empty `tests` array; open issues #6213 and #6256 and the fixed #6255 are all this bug in the vitest-runner. A Playwright runner that filters to zero tests, or whose page fails to load, must not report Survived. Section 1.1. [checked]
- **Fixed per-run timeouts as infinite-loop detection.** grunt-mutation-testing's 2 s wait "may trigger false positives"; PIT's FAQ: classloading under mutation turns millisecond tests into seconds, causing false timeouts. Use Stryker's `netTime * factor + constant` plus `hitLimit`. Sections 1.1, 1.2. [checked]
- **Raising parallelism to go faster on a shared server or database.** Timeouts rise and the score moves (mutmut #545, stryker-js#5284, Infection #1671 where parallel runs reported a false 100% MSI). Sections 1.2, 5.2. [checked]
- **Split-stream, fork and state-equivalence speedups.** MuVM, AccMut and infected-state partitioning need one process that can fork at the mutation point; browser + server + test worker has none. Section 2.3. [inferred from checked mechanisms]
- **In-process activation mechanisms for an out-of-process server.** PIT's hot swap, Mutant's monkeypatch, Infection's include interceptor and Major's config class never reach a separately started process; that is why none of those ecosystems has an e2e story and why PIT's author calls integration-test mutation "not usually recommended" (#827). Section 1.2. [checked]
- **Stryker worker processes launching remote browsers through Selenium Grid / Docker.** stryker-js#1985 died on DNS resolution inside the child process and was closed unresolved; the WCT/selenium runner was dropped in Stryker 4 (#1487). Section 1.1. [checked]
- **Waiting for an upstream runner.** Feature requests for Cypress (#3856, 2022) and Web Test Runner (#4489, 2023) went stale; cypress#16299 has been open since 2021; nothing exists on npm or GitHub for Playwright beyond two demo repos. Sections 1.1, 4. [checked]
- **Expecting e2e suites to score like unit suites.** Mutta reached 12.5% of mutants on a realistic app and killed 39-52% of those; Facebook's combined unit + integration + e2e suites let more than half of mutants survive; web interaction mutants are killed 47% of the time by traditionally designed tests. Report e2e mutation scores on covered mutants, scoped to a handful of files, and expect oracle quality to dominate. Sections 2.1, 2.3, 2.4. [checked]
- **Writing a runner on the assumption that `__stryker__` is a stable API.** stryker-js#6238 (open) states it is undocumented; the Vitest runner and karma runner use it from inside the monorepo. Pin the Stryker major version and read `INSTRUMENTER_CONSTANTS` from `@stryker-mutator/api/core` instead of hard-coding names. Section 1.1. [checked; the recommendation is inferred]
